# FCP、LCP 与图片传输优化设计

## 背景

站点采用 Next.js 16 Pages Router 静态导出，并部署到 GitHub Pages。当前页面将 Google Fonts 样式表作为渲染阻塞资源；`next.config.ts` 为静态导出启用了未优化图片；六张“团队介绍”图片以 1,350–2,400px 的原始尺寸提供。`Hero`、`Layout` 和首屏以外的组件也让 Framer Motion 进入初始客户端包。

现有静态资源约为 4.2 MiB，其中“团队介绍”图片约为 4.1 MiB。这些事实对应 Lighthouse 报告中的渲染阻塞请求、约 2.4 MiB 的图片传输节省机会和主线程工作负担。

## 目标与验收

在同一台机器、Lighthouse 的移动端默认模拟配置、无缓存的生产构建中，连续运行三次，以中位数验收：

- FCP 不高于 1.0 秒。
- LCP 不高于 1.0 秒。
- 初始页面不请求首屏以外的内容图片；总图片传输量显著低于当前约 4.2 MiB。
- 不改变现有中文手绘视觉、导航结构和 `prefers-reduced-motion` 行为。

1 秒为实验室性能预算。真实用户体验的长期兜底指标为 LCP 第 75 分位不高于 2.5 秒；网络、设备与 CDN 命中情况不纳入 1 秒实验室预算的保证范围。

本次不迁移 App Router、不改变 GitHub Pages 部署方式，也不引入运行时图片优化服务。

## 方案选择

选择“保留现有设计的静态资源优化”方案：本地化字体、生成响应式静态图片、从首屏包中移出非必要动画运行时，并通过静态导出产物和 Lighthouse 复核。

仅压缩原图不能消除字体阻塞和 JavaScript 负担；替换为系统字体并删除所有动画虽能获得更大余量，但会不必要地改变站点视觉和交互。

## 设计

### 字体与首屏关键路径

将 `_document.tsx` 中的外部 Google Fonts 预连接和样式表链接替换为 Next.js 的自托管字体机制。保留 Patrick Hand、Space Mono 和 Noto Sans SC 的现有字体角色与所需字重，使用 `display: "swap"` 与匹配的后备字体栈。

这样首屏不再等待第三方 CSS；字体文件由静态导出产物以本地资源形式提供。字体下载失败时，文本立即以定义的后备字体渲染，不阻塞 FCP 或 LCP。

`Hero` 和 `Layout` 只保留静态 React/DOM 能力：去除没有必要的 Framer Motion 包装与顶层 `MotionConfig`。首屏标题、文案和 Logo 在初始 HTML/CSS 中完整可见，LCP 不依赖动画库下载或 hydration。

### 图片资源与加载策略

为团队介绍的每张图片生成按实际显示宽度设计的 WebP 变体，提供移动端与桌面端候选尺寸；最大候选尺寸不超过实际布局需要的两倍。二维码按其最大显示尺寸生成较小变体。Logo 保持现有轻量资源，但声明原始宽高。

在数据层集中管理图片的路径、宽高和候选资源。组件通过 `<picture>`/`srcset` 与 `sizes` 选择合适资源，并始终输出 `width`、`height`、`loading="lazy"` 和 `decoding="async"`。只有确认的首屏 LCP 图片才可声明高优先级；当前页面首屏是文案与小 Logo，因此团队介绍图片和二维码都保持惰性加载。

构建生成的图片使用内容指纹文件名。GitHub Pages 不支持为本项目任意配置缓存响应头，因此不能承诺通过应用代码把 Lighthouse 的“缓存生命周期”审计降为零；指纹文件名可确保缓存更新安全，并避免部署后同名旧图被误用。

缺少候选资源、尺寸元数据或静态路径时，应在构建/测试阶段失败，而不是在浏览器中静默请求原始大图。

### JavaScript 与非首屏内容

将依赖 Framer Motion 的非首屏区块拆分为延迟加载边界，确保其运行时不属于首屏必需 JavaScript。关键文案区块维持服务端静态输出和可访问语义；延迟模块加载前保留稳定的最小占位空间或静态内容，以避免布局跳动。

动画模块加载失败时，区块仍以静态内容展示，导航锚点和键盘访问保持可用。减少动态效果偏好继续由现有逻辑控制。

### 验证与测试

实现先为每个新增资源契约写失败测试：图片清单包含有效尺寸和响应式资源，首屏组件不再引入动画运行时，字体不再通过外部 Google CSS 链接加载。测试通过后再实现最小变更。

验证包括：

1. 运行相关 Vitest 测试、完整测试套件和 ESLint。
2. 用 `NEXT_PUBLIC_BASE_PATH=/LecOrg` 运行静态构建，检查导出的 HTML、字体资源、图片 `srcset` 和 GitHub Pages 路径。
3. 用相同 Lighthouse 移动端配置对优化前后构建各运行三次，记录中位数 FCP、LCP、总图片传输量和主线程时间。
4. 宽度为移动端与桌面端各执行一次浏览器检查，确认图片候选选择、懒加载、锚点导航、字体回退和降低动态效果均正常。

## 影响范围

预计涉及字体初始化、图片资产与其数据映射、`Hero`/`Layout`、含图片的区块组件、以及延迟加载边界和相应测试。不会修改团队内容数据、路由、页面结构或部署工作流的职责。
